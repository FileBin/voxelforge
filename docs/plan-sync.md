# План: убрать последнюю синхронизацию с CPU

Живая симуляция — `crates/world/src/bin/voxelforge_live.rs` + `crates/world/src/live.rs`.
Счётчики — на одного такта физики (64 тела максимум).

## Что есть сейчас

| обмен | объём | когда | как называется |
|---|---|---|---|
| позы GPU→CPU | 7 168 Б | **каждый такт** | `read_bodies` |
| энергия удара GPU→CPU | 2 048 Б | **каждый такт** | `read_impact` |
| тела CPU→GPU | 7 168 Б | по событиям | `write_bodies` |
| пул тетов CPU→GPU | ~2 КБ × тел | по событиям | `upload_geometry` |

Оба «каждый такт» — обычный `memcpy` из mapped-памяти (`vf_buffer_read`), без
отдельного ожидания: ожидание одно на такт, внутри `vf_run`. То есть дорого не
чтение, а то, что CPU **держит зеркало состояния физики** и обновляет его
каждые 50 мс.

## Шаг 0 (предусловие для шага 1): один Vulkan-девайс

Сейчас **два независимых устройства**: `c/voxelforge_core.c` создаёт своё
(`vkCreateInstance` + `vkCreateDevice`), `c/voxelforge_view.c` — своё. Буферы
друг друга они не видят, поэтому рендер физически не может прочитать буфер тел.

Нужно:
1. `voxelforge_core.c`: отдать наружу `VkInstance`, `VkPhysicalDevice`,
   `VkDevice`, очередь и семейство очередей (`vf_ctx_device()`).
2. `voxelforge_view.c`: не создавать своё; принимать их в `vf_view_new` и
   работать через `vkGetDeviceProcAddr`/переданные таблицы, свои буферы
   выделять на том же девайсе.
3. Согласовать `VK_KHR_swapchain` + surface: поверхность создаётся на общем
   instance — значит instance должен включать `VK_KHR_surface` и расширения
   оконной системы ещё в ядре.

## Шаг 1: `read_bodies` → рендер прямо из буфера тел

После шага 0:
1. `vf_view_set_bodies(view, VkBuffer, uint32_t n)` — дескриптор SSBO на буфер
   `bodies[0]` ядра (он же пинг-понг `bodies[1]`; нужен текущий).
2. Вершинный шейдер меша читает позу по индексу: `pos_r`, `quat` из `Body`
   (112 Б), строит матрицу сам; `vf_view_draw` получает номер тела вместо
   матрицы.
3. Интерполяция `prev → текущий` переезжает в шейдер: ядро пишет вторую позу
   (`prev_pos_r`, `prev_quat`) в тот же `Body` — 32 Б на тело, без нового буфера.
4. `LiveBody` теряет `pos`, `quat`, `vel`, `mass` — остаются `id`, `tets`,
   `mesh`, `kind`, `alive`.
5. `read_bodies` не нужен вовсе.

Риск: пункт 3 меняет картинку (сглаживание движения считается на GPU) —
проверять глазами.

## Шаг 2: `read_impact` → раскол на устройстве

1. Решение о расколе принимает шейдер: энергия уже есть в `impact.comp`.
2. Геометрию осколков делает CPU (мешер), поэтому событие всё равно должно
   доехать до CPU. Дешёвый путь без чтения каждый такт: GPU пишет компактную
   очередь событий `(тело, энергия, точка)` в кольцевой буфер и атомарно
   увеличивает счётчик; CPU читает **счётчик** (4 Б) и только при изменении —
   сами события. При спокойной сцене чтений нет вообще.
3. Порог энергии (сейчас 500 Дж) переносится в шейдер, чтобы события писались
   уже отфильтрованными.

## Шаг 3: `write_bodies` → спавн на устройстве

1. Добавление тела: GPU-проход `body_init.comp` по команде из кольца команд
   (спавн снаряда, появление осколка) — CPU кладёт в очередь только
   `(позиция, поворот, скорость, масса, ссылка на пул тетов)`.
2. Деспавн (пул снарядов `MAX_BULLETS = 12`) — тот же проход с флагом
   `misc[1] = 1`.
3. Пока шаг не сделан, `write_bodies` остаётся событийным и это нормально:
   7 КБ при спавне/расколе, не каждый такт.

## Шаг 4: `upload_geometry` → мешер на устройстве (не обязательно)

Пул тетов строится на CPU (марчинг, red-разбиение). Переносить мешер на GPU
имеет смысл только если раскол пойдёт десятками в секунду; сейчас заливка
только по событиям и стоит копейки. **Предлагаю не делать.**

## Порядок

0 → 1 (убирает 7 КБ и зеркало поз) → 2 (убирает 2 КБ) → 3 (по желанию).
Шаг 0 — единственный структурный: пока девайсы разные, шаг 1 невозможен.

## Состояние: синхронизаций с тактом нет

Ветка `device-merge`. Проверено: `nix run .#headless` (exit=0, трещины есть),
`cargo test --locked` (зелёный), `nix run .#probe -- probe_bytes` (12 Б/такт),
`probe_fastshot` (трещины на 26/60/120/240 м/с).

- **шаг 0 — один девайс.** `vf_ctx` (`c/voxelforge_core.c`) создаёт instance с
  surface-расширениями (`vf_init_for_window`) и устройство с графикой и
  `VK_KHR_swapchain`; окно (`c/voxelforge_view.c`) берёт
  `VkInstance/PhysicalDevice/Device/Queue` у ядра, создаёт только поверхность и
  swapchain. Очередь одна на физику и кадр: submit'ы под мьютексом `vf_ctx`,
  ожидание fence — вне замка. В начале кадра окно ставит барьер
  compute→vertex: такт отправляется асинхронно, и без барьера вершинный шейдер
  мог не увидеть запись compute.
- **шаг 2 — кольцо событий раскола.** `impact.comp` пишет событие
  (энергия, тело, партнёр / нормаль / точка) в кольцо на 128 записей и
  увеличивает счётчик; порог (500 Дж) — в шейдере (`pc.lo.w`, поле `lo.w`
  раньше пустовало). Счётчик обнуляется в начале такта, поэтому CPU читает
  «сколько событий» и не хранит номер последнего.
- **шаг 1 — поза из буфера тел.** `Body` вырос до 144 Б (`prev_pos_r`,
  `prev_quat`), проход `snapshot.comp` в начале такта пишет прошлую позу,
  `view_mesh.vert` строит матрицу сам и интерполирует по `alpha`. CPU не
  присылает матрицы и не считает сглаживание; каркас (`T`) — по-прежнему на
  матрицах и только для отладки.
- **без стойки CPU.** `vf_run_async` отправляет такт и не ждёт; кольцо из
  трёх command buffer'ов и fence'ов, слот переиспользуется только когда его
  fence закрыт. `vf_wait_back(c, n)` ждёт такт, отправленный n submit'ов назад.
  В начале такта CPU ждёт ПРОШЛЫЙ такт (он давно закрыт — такт раз в 50 мс),
  забирает статистику и события и только потом отправляет новый.
- **чтение тел из такта убрано.** `stats.comp` отдаёт 8 Б (максимум |v| и число
  бодрствующих), плюс 4 Б счётчика событий — **12 Б/такт** в спокойной сцене,
  CPU→GPU — 0.
- Позы на CPU подтягиваются только по событию: раскол (одно тело через
  `read_body` в `split`), спавн/деспавн снаряда и выключение сна (там
  `write_bodies` заливает буфер целиком), включённый каркас.
- **Грабли, которые стоили проверок** (не повторять):
  * `write_bodies` заливает ВЕСЬ буфер, поэтому перед ним нужно `sync_all()`,
    иначе остальные тела уезжают назад к моменту прошлого чтения;
  * `chunks` (нарезка такта на куски) считается по статистике ПРОШЛОГО такта, а
    на такте выстрела снаряда в ней ещё нет — без `pending_vmax` нарезка
    оставалась 2, и снаряд на 120 м/с перескакивал плиту (`probe_fastshot`);
  * `Drop` для `GpuSim` обязан сначала `vf_idle`: такт в полёте, и
    освобождение буферов под работающим GPU роняло драйвер на втором мире в
    одном процессе.

Осталось: шаг 3 (`write_bodies` → очередь команд) — по плану «по желанию»;
сейчас запись тел идёт только по событиям (выстрел, раскол, сброс), не в такте.

## Две очереди: дефолт, замки, фазы кадра (замеры на RX 6600)

Разделение очередей сделано (такт — compute 0.0, кадр — graphics 1.0,
таймлайн-семафоры, банк `tick % 2`), но оставался ряд сталлов. Убрано:

- **Две очереди теперь по умолчанию.** Раньше включались только `VF_SPLIT`, и
  `nix run .#live` шёл по одной очереди. Старый путь — `VF_QUEUES=one`
  (алиас `VF_SPLIT=0`); новый — дефолт.
- **Замок на ОЧЕРЕДЬ, а не общий** (`vf_queue_lock(c, stream)`): при двух
  очередях у кадра и такта свои замки — `present` (FIFO ждёт развёртку) больше
  не блокирует submit такта, а запись 2000 диспатчей не блокирует кадр.
- **Два кадра в полёте** (`VF_FIF=2`, `VF_FIF=1` — старый путь): command buffer
  fence, семафор образа, UBO, набор и глубина — свои на слот/образ. Раньше CPU
  на каждом кадре ждал fence своего же кадра.
- **Пары тетов — внутри такта** (`tet_pair_steps`, один submit): отдельный submit
  с `vf_run` держал поток физики до 57 мс/такт. `VF_PAIRS_OLD=1` возвращает
  старый путь.

Диагностика (`VF_PERF=1` / F3) — два новых блока. «такт на CPU»: ожидание fence,
чтения обратно, запись команд, замок очереди, `vkQueueSubmit`, итого. «кадр»:
`wait fence · acquire · record · lock sub · submit · lock pres · present ·
interval · gpu idle` (min/mean/max/p99 за 1 с); те же строки в оверлее.
Два графика под строкой частот — работа кадра (record+lock+submit, сумма фаз) и
работа такта («ИТОГО такт»), линии бюджета 16.7 / 50 мс; fps/tps остаются числом.

Замер (живое окно, RADV NAVI23, «плита + выстрелы», `VF_CHUNKS=4`):

| | одна очередь, 1 кадр, sync-пары | дефолт (две очереди, 2 кадра, пары внутри) |
|---|---|---|
| интервал кадра | 58-74 мс (14-17 fps) | **16.7 мс (60 fps)** |
| простой GPU между кадрами | 58-78 мс | 16.2 мс |
| такт на CPU | 58 мс (53 — ожидание пар) | **0.5 мс** |
| ожидание fence кадра | 2.7 мс (макс 5.9) | 0.003 мс |

Остаток (не сталл): при 20 телах такт на GPU ~120 мс, из них генерация пар
(`tet_pairs_flat`) 27.6 среднее / 107 максимум = 58%; солвер ~2.5 мс. Кадры
падают до 30 fps именно из-за этого бюджета (GPU занят тактом, композитор
опаздывает), а не из-за ожиданий: `замок очереди` 0.001 мс, `ожидание fence`
0.014 мс при такте 33 мс.
