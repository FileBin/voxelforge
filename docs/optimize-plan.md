# План оптимизации (ветка `optimize`)

Отправная точка: тег `first-working` (`1257c0a`). Всё, что ниже, измерено на
этой сборке, а не взято из общих соображений.

## Замер, с которого начинаем

Сцена: плита расколота, 12 снарядов выпущены одновременно, в мире 22 тела.
Замер `VF_TIME=1` (внутри `Live::step`), среднее по 60 кадрам:

| фаза | среднее | макс |
|---|---|---|
| контакты (CPU, SAT по тетраэдрам) | **209.2 мс** | 263.2 мс |
| позиционная развязка (CPU) | 0.03 мс | 0.05 мс |
| солвер (GPU: 6 чанков × 4 подшага × 10 итераций) | 6.2 мс | 8.0 мс |
| раскол | 0.01 мс | 0.01 мс |
| **кадр целиком** | **216.7 мс** | 270.2 мс |

Вывод: 97% кадра — коллизия на CPU. Никакая переделка солвера сама по себе
FPS не поднимет, пока контакты считаются на процессоре и каждый кадр ездят
туда-обратно.

## Порядок работ (по убыванию выигрыша)

### Этап 1. Коллизия на GPU — убирает и 209 мс, и зеркало

Сейчас на кадр приходится: `collide::build` (SAT, CPU) → `write_contacts`
(CPU→GPU) → солвер → `read_bodies` (GPU→CPU) → CPU переписывает позиции в
`self.bodies`. Это и есть «зеркало», которое не нужно.

1. **Геометрия тел живёт на GPU.** Один пул тетраэдров (`vec4 a, vec4 b, vec4 c,
   vec4 d` на тет или 4×vec3) + на тело `{tet_offset, tet_count, quat, pos}`.
   Заливается один раз при создании/расколе, а не каждый кадр.
2. **Broadphase на GPU.** Равномерная сетка или хеш по AABB тетов: считаем
   ключ ячейки, `atomicAdd` в счётчики, второй проход раскладывает пары.
   Порядок пар не фиксирован, поэтому пары сортируются по ключу (иначе
   результат не воспроизводится — та же ошибка, что с `HashMap` на CPU).
3. **Narrowphase на GPU.** SAT по 8 нормалям граней + 36 рёберным осям на пару,
   контакты пишутся в буфер и в CSR-списки по телам (`body → [contact]`).
4. **CPU больше не трогает позиции каждый кадр.** Читает только то, что нужно
   геймплею: события (раскол, вылет за пределы) — редкие, раз в несколько
   кадров, через отдельный лог.

Ожидание: 209 мс → единицы миллисекунд; кадр перестаёт зависеть от числа
контактов на CPU. Это же снимает ограничение на число тел (сейчас потолок —
производительность SAT на процессоре).

### Этап 2. Солвер: параллельно по КОНТАКТАМ, а не по телам

Сейчас один вызов солвера на тело, и внутри цикл по его контактам: у тела с
24 контактами работа в 24 раза больше, чем у тела с одним — ровно та
неравномерность, о которой речь.

Как надо (как и задумано):

1. **Проход A — по точкам контакта.** `dispatch(bodies × CAP)` — работа строго
   одинаковая. Каждый контакт считает свой импульс от снимка скоростей и
   пишет две четвёрки (`dv`, `dw`) в массив по индексу `body*CAP + k`.
2. **Проход B — по телам.** `dispatch(bodies)`: суммирует `CAP` записей своего
   тела, применяет один раз с релаксацией, пишет скорость.

Арифметика та же, что сейчас (включая деление на число контактов пары), просто
сумма переезжает из регистров одного вызова в отдельный проход. Побочный плюс:
порядок суммирования фиксирован (по `k`), значит результат не зависит от того,
как GPU распланировал вызовы.

Почему не первым: это 6 мс из 216. Делать после этапа 1, иначе выигрыш не виден.

### Этап 3. Никакого зеркала состояний

- `Live::mirror: Vec<GpuBody>` — это CPU-копия тел, которую каждый кадр
  перезаписывают и туда, и обратно. После этапа 1 она нужна только для
  спавна/раскола; в кадре её быть не должно.
- Сон, якоря, пробуждение по контакту — на GPU (у солвера уже есть все
  контакты, ему и решать).
- Раскол: CPU получает событие «такое тело получило такую энергию», режет
  геометрию и заливает новые тела — раз в событие, а не каждый кадр.

## Что не делать

- Не распараллеливать солвер в надежде поднять FPS, пока контакты на CPU:
  это 3% кадра.
- Не переносить в GPU то, что случается редко (раскол, спавн): выигрыша нет,
  сложности много.
- Не полагаться на порядок пар из `atomicAdd` — сортировать по ключу.

## Замер копий (этап 3, с чего начинать)

Счётчики `GpuSim::bytes_up/bytes_down`, сцена 22 тела, такт 1/20:

| направление | за такт |
|---|---|
| CPU → GPU | 83 КБ |
| GPU → CPU | 83 КБ |

Сам по себе объём небольшой (при 20 Гц это ~3.3 МБ/с), и бороться нужно не
с ним, а с **числом синхронизаций**. На каждый «кусок» шага сейчас
приходится: заливка контактов → `vkQueueSubmit` → ожидание fence →
`vkMapMemory` тел → снова submit. Кусков 6–12 за такт, то есть 12–24
round-trip'а, и каждый — остановка очереди.

Отсюда вывод: убирать надо не байты, а **сабмиты**. Один submit на такт
возможен только если контакты считаются на устройстве: тогда broadphase,
SAT, солвер и интегрирование идут одним командным буфером, а CPU читает
состояние раз в такт (или вообще только события). Это и есть этап 1.
