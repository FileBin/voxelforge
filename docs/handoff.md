Точка, на которой остановились. Всё, что ниже, проверено на этой ветке.

## Ключевые баги, уже исправленные (не переделывать)

- порядок кватерниона в шейдерах: `(w, x, y, z)`, скаляр в `.x` — из-за `.xyz/.w`
  SAT считал чужие оси (симптом: снаряд проходит сквозь плиту, кубы «как шары»);
- собственный момент тетраэдра в `solid_inertia` (иначе у осколка из 1 тета
  момент ≈ 0 и его раскручивает любой импульс);
- фрикционный импульс делится на число контактов так же, как нормальный;
- предел трения в единицах импульса: `cap = mu * max(dl, 0.02 / wn)`;
- пол/стены — по вершинам тетов, пол даёт 4 угла опоры (иначе куб крутится
  юлой: опора в одном углу, плеча нет);
- `static_contacts`: глубины стен инициализировать `-1e9`, а не `0` (иначе все
  четыре стены срабатывают каждый подшаг и снаряд теряет скорость);
- сетка пар CPU выровнена с шейдерами: начало `lo`, размеры `ceil((hi-lo)/cell)`.

## Пары на устройстве: работает (VF_PAIRS=gpu)

`tet_key` → `tet_scan` → `tet_fill` → `tet_pairs` подключены в `step_gpu` под
флагом окружения `VF_PAIRS=gpu`. В этом режиме из кадра уходят и заливка пар,
и чтение позиций тел: на CPU приходит только число пар (4 байта).

Сверено по шагам: сетка — 4132 записи/225 ячеек, 0 расхождений с CPU; пары
уникальны (дедуп по минимальной общей клетке).

Остаток расхождения: на GPU нет префильтра `allow[]` (пересечение AABB тел),
поэтому пар 15493 против 3366 у CPU — лишние отсеивает SAT, но это время.
Headless при равных прочих: GPU-пары 17 тел / 6 трещин / 19 осколков против
CPU-пар 20 / 9 / 25.

Следующий шаг: тот же префильтр на устройстве — маска тел (64 тела = один u64
на тело) считается мини-проходом, `tet_pairs` её читает и выбрасывает пары
тел без пересечения AABB.

## Где именно застряли

`tet_pairs` даёт 310 пар против 3366 у CPU. Дамп ячеек показал: в клетках лежат
записи **одного тела** (например 12 записей, все тело 3). Значит до испускания
пар дело не доходит — межтелесных соседей в клетке нет, хотя у CPU они есть.

Следующий замер (один): взять конкретную клетку, где находится снаряд, и
напечатать список тел из GPU-раскладки рядом с CPU-списком. Если у CPU там оба
тела, а у GPU только снаряд — искать в `tet_fill`: какие ячейки получает
крупное тело (проверить `span`, позу на момент раскладки, размеры сетки).

## Как проверять

```
# сверка сетки
cargo run -q --release -p voxelforge-refsim --example probe_grid
# сверка пар
cargo run -q --release -p voxelforge-refsim --example probe_pairs_gpu
# сверка SAT пары-в-пару
cargo run -q --release -p voxelforge-refsim --example probe_pair
```

## Что осталось после broadphase

1. подключить `tet_pairs` в `frame_gpu_contacts` перед `sat`;
2. убрать `set_pairs` и `read_bodies` из `step_gpu` (`read_bodies` — только под
   `VF_DEBUG=1`);
3. события раскола: GPU пишет (тело, энергия, точка) в буфер, CPU читает
   десятки байт вместо списка контактов;
4. известные дефекты физики: осколок на ребре качается (нет сопротивления
   качению в контакте), вращение зависит от числа проходов (нужен accumulated
   impulse / warm start).

## Интерполяция кадра (почему дрожало и как починено)

Симптом: при такте 20 Гц и 60 кадрах/с объекты дрожали «парами кадров», на
30 Гц; без интерполяции — ровно.

Две причины, обе — рассогласование пары `prev→cur` на устройстве и `alpha` на CPU:

1. **Кадр собирался, пока такт в полёте.** Позы в буфере тел меняет сам такт
   (integrate_pos), поэтому на момент исполнения кадра на GPU там могло лежать
   состояние НОВЕЕ опубликованного; `alpha` же считалась от прошлой публикации.
   Кадр рисовал новую пару со старым `alpha` → прыжок на такт вперёд, а после
   публикации `alpha` обнулялась → отпрыгивание назад.
   Лечение: перед сборкой кадра ждём флага `in_tick` (такт закрылся). GPU одна
   очередь и так ждал бы такт, так что CPU-ожидание ничего не добавляет.

2. **`alpha` делилась на номинальный такт.** Публикации приходят реже номинала
   (сам такт считается 10–30 мс + `sleep(1 мс)` в потоке), поэтому `alpha`
   упиралась в 1 задолго до нового снимка: картинка замирала и потом прыгала.
   Лечение: делитель — измеренный интервал между публикациями (EMA 0.8/0.2).

Что НЕ надо делать (проверено, не помогает или вредит):

- читать счётчик завершённых тактов из потока рендера и сбрасывать по нему
  `alpha` — окно всё равно остаётся, а чтение буфера с хоста гонки не ловит;
- две очереди + таймлайн-семафоры для такта и кадра: на RADV дало GPUVM fault
  (`SQC`, чтение по мусорному адресу) при первом столкновении, контекст терялся.
  Прежде чем пробовать снова — двойной банк состояния тел на очередь;
- MAILBOX вместо FIFO: ритм начинает задавать `sleep`-ограничитель, фаза с
  композитором не совпадает — камера дёргается. FIFO + ограничитель не нужен.

Swapchain: `minImageCount + 1` образов (`VF_SWAP=N`), режим FIFO по умолчанию
(`VF_PRESENT=mailbox|immediate` для сравнения).

## Что осталось (порядок работ)

1. **Красный тест `fragments_settle_without_jitter`** — осколки не успокаиваются
   (7–9 м/с через 600 кадров). Проверено в worktree на `cd55bbc` и `684651f`:
   падал и до всех правок этой сессии, то есть это НЕ регресс, а качество
   солвера. Итерации 10 → 18 дают 9.5 → 5.5 м/с (порог 0.02), значит дело в
   сходимости: без накопленных импульсов (warm start) кучка осколков не гаснет.
2. **Параллельный скан** (`VF_SCAN=parallel`) ломает первый такт: с ним
   `first_shot_breaks_the_whole_plate` красный, плита не раскалывается.
   Сверка `probe_scan` (обе реализации на одних данных в одном процессе) даёт
   0 несовпавших ячеек, значит ошибка не в самих числах префикса, а в связке с
   последующими шагами — вероятно, `start[nc]` пишется в проходе 2
   (`tet_blockprefix`), а третий проход не пересчитывает курсоры для последней
   неполной группы.
3. **Равномерность пар** — главная задача по нагрузке. Сейчас одна invocation
   на ячейку и O(k²) внутри; на целом кубе 161–205 тыс. итераций дают 0–35 тыс.
   полезных пар, а время такта определяет самая плотная ячейка. План: префикс по
   числу потенциальных пар `k(k-1)/2` на ячейку, затем одна invocation на пару с
   бинарным поиском своей ячейки. Скан для этого уже есть.
4. После зелёного п.1–2 — включить параллельный скан по умолчанию.

Инструменты: `probe_scan` (сверка сканов), `probe_pairs_cost` (распределение
пар по ячейкам), `probe_pair_stick` (два кубика навстречу), `VF_SCAN`,
`VF_CHUNKS`.

## Открыто: дрожание кадра вернулось на сетке Сомирвилля

Симптом: «каждый второй кадр перепутан» — снова, после перехода тел на тет
Сомирвилля (bcc_tets). Компенсация по перегрузке такта (`overdue` →
alpha = 1) не лечит, только маскирует: пара prev→cur всё равно меняется
не в такт с alpha.

Рабочая настройка сейчас: `VF_NO_INTERP=1` — кадр рисует точное состояние
такта, дёрганья нет.

Настоящее лечение (порядок):
1. **Канонизировать тет в одну ячейку.** Тет Сомирвилля пересекает границу
   кубической ячейки, поэтому попадает в две: записей (ячейка, тет) больше,
   пар — квадратично больше, такт не влезает в 20 Гц. Регистрировать тет в
   ячейке его центроида, соседей искать по 27 окрестным ячейкам.
2. **Рисовать на такт позади.** CPU держит два опубликованных снимка поз
   (prev/cur) и alpha по времени публикации; кадр никогда не смотрит на пару,
   которую сейчас пишет GPU. Стоит ~50 мс задержки, но неуязвимо к длительности
   такта — в отличие от ожидания `in_tick`, которое само создаёт рывок.
3. Только после (1)+(2) — включать интерполяцию по умолчанию.
