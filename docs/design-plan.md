# План перехода на GPU-driven движок

> **Актуализация (voxelforge).** Игру пока не делаем. Ближайшая форма работ —
> **демки с физическими симуляциями**, каждая из которых является приёмочным
> тестом: гравитация и орбиты, посадка на планету, стопка, куча тел, грануляр,
> столкновение крупных объектов, нагрев и слияние, обломки. Таблица демок с
> критериями — в корневом `README.md`; она заменяет «Этап 6» (Rust-хост целиком)
> и «Этап 7» (сеть) как ближайшие цели. Этапы 0–5 остаются в силе: контракт
> кадра, шлюзы детерминизма, камера, C-ядро.
>
> Текст ниже сохранён как исходный дизайн-документ, из которого выросли решения
> (он же лежит в `SandboxGame/docs/gpu-driven-refactor-plan.md`).

Цель: симуляция, рендер и события живут в VRAM. CPU — окно, ввод, I/O, сеть.
Симуляция не крутится на CPU ни в одном кадре.

Текущее состояние (замерено в этом репозитории, 2026-11):

| Часть | Где | Размер |
|---|---|---|
| Vulkan-слой движка | `RiceEngine/GL` (`.hpp` + `_impl.inl`) | 3356 строк, из них `Vulkan_API_code` — 3185 |
| GPU-слой игры | `src/gpu` (`GpuTetOctMesher`, `GpuTetraMesher`, `FieldBricks`) | 1092 строки |
| Чистая логика мира | `src/world` | 23 файла, движок не знает |
| Движок целиком | `RiceEngine-game` | ~6335 строк `.cpp` |

Вывод: целевое C-ядро — это **~4.5k строк**, примерно размер уже существующего
слоя. Речь не о новом движке, а о переписывании `GL/` из CRTP-пар в plain C
функции и выносе `src/gpu` за C ABI. Ориентир по бюджету: C-слой держать
меньше ~5k строк, иначе он станет худшей частью проекта.

## Порядок

Архитектура → контракт кадра → шлюзы детерминизма → камера → C-ядро → Rust-хост
→ сеть. Обратный порядок (сначала язык) — два переписывания вместо одного.

### Этап 0. Спайк (1–2 вечера)

Отдельный репозиторий `rust-vk-spike`, ничего в текущем не трогаем.

- один командный буфер, записанный один раз, indirect-размеры из SSBO;
- input-ring на `M = framesInFlight + 1` слотов;
- одно тело на GPU, камера `C⁻¹·B⁻¹` с экстраполяцией по скорости;
- лог событий со счётчиком и `atomicExchange` для одноразовых;
- замер: CPU-время на кадр через timestamp queries.

Корректность — на lavapipe. **Числа производительности — только на реальном GPU
и только с явного разрешения** (иначе цифры будут ложью).

Шлюз: есть измеренная цифра «CPU на кадр» и ответ, устраивает ли эргономика
`ash` в `unsafe`.

### Этап 1. Замки архитектуры (дни, документы)

Четыре решения, дешёвые сейчас и дорогие потом. Записать в `docs/`:

1. воксельные данные — целые (int16 + целочисленный хеш генерации), математика
   float;
2. единственная форма мутации мира — журнал правок (`EDIT ...`), плюс undo-лог
   по брикам для откатов;
3. снапшот-кольцо с маркерами шага (сеть читает по шагу, не по кадру);
4. авторитетный сервер — lavapipe или хост игрока; вторая реализация физики на
   CPU не берётся.

Шлюз: решения записаны до первой строки симуляции, а не после.

### Этап 2. Контракт кадра в текущем движке (1–2 недели)

Ветка `ai/gpu-frame-contract` в `RiceEngine-game`. Ценно даже если переезд в Rust
не случится.

- один CB на образ swapchain, записан один раз, пере-сабмитится;
- все размеры работ — из SSBO (`vkCmdDispatchIndirect`, `vkCmdDrawIndirectCount`);
- bindless input-ring вместо per-frame UBO и ре-биндов;
- убрать `vkMapMemory` из кадрового цикла, только кольцо + fence.

Шлюз: CPU-время кадра измерено до/после; в RenderDoc видно, что кадр не
перезаписывается с CPU.

### Этап 3. Шлюзы детерминизма (дни)

- `templates/det.h` — макросы на именованные `sqrt/sin/pow` (ловят по имени,
  `normalize()` не ловят);
- `scripts/check-shader-determinism.sh` — скан SPIR-V на `OpExtInst`/`OpAtomic`
  (ловит раскрытия: `normalize`, `length`, `distance`, `reflect`, `refract`);
- twin-run: два прогона солвера с одинаковым входом, `memcmp` состояния — ловит
  гонки, которые статика не видит;
- правило солвера: gather-only (Jacobi) — читаю прошлый шаг, пишу свой слот, без
  атомиков.

Шлюз: гейт падает на специально испорченном шейдере и проходит на чистом.
Проверять падение, а не только успех.

### Этап 4. Камера из физического тела (дни)

- `proj · C⁻¹` от CPU (камера «в вакууме»), `inverse(bodyWorld)` от GPU;
- экстраполяция `pos + vel·dtToNow`, `dtToNow` из GPU-шага;
- кламп экстраполяции коротким SDF-маршем, иначе камера на кадр уходит в стену;
- **правило**: все проходы, трогающие мировые позиции (куллинг, LOD, SDF, тени,
  debug), используют ту же матрицу. Смешали пространства — мир уезжает при
  повороте головы.

Шлюз: камера не проходит сквозь геометрию, куллинг консистентен с рендером.

### Этап 5. C-ядро `vkcore` (2–4 недели)

Вынос `RiceEngine/GL` + `src/gpu` за C ABI, coarse-grained API (~30 функций:
устройство, swapchain, пайплайн, дескрипторный хип, upload брика, submit кадра,
дренаж событий).

- `bindgen` читает C-заголовки, поэтому граница дешёвая; Vulkan-типы наружу не
  выставляются;
- вызовы только Rust → C, колбэков нет;
- ни логики, ни состояния мира, ни алгоритмов в C;
- ошибки — коды + C-статик, не enum'ы;
- `VK_NO_PROTOTYPES`: функции выше 1.0 грузить через `vkGetDeviceProcAddr`.

Шлюз: Rust-хост дергает диспатч через `cc`-сборку в `build.rs`, игра
запускается headless на lavapipe.

### Этап 6. Rust-хост (3–6 недель)

Порядок переноса: input-ring → дренаж событий → стриминг (`io_uring`) →
save/load → UI. `src/world` переносится по одному модулю, `cargo test` как
оракул (standalone-тесты уже есть в `tests/`). `scripts/headless-run.sh`
переносится 1:1.

Шлюз: паритет с текущей игрой по headless-метрикам (`chunks`, `tris`), затем
снятие C++ движка.

### Этап 7. Сеть (отдельная фаза)

Только после этапов 2–4. State-sync (не rollback), снапшоты 20 Гц, журнал
правок, hit-валидация откатом позиций, сервер на lavapipe — **сначала замерить,
потом обещать**.

## Новый репозиторий

Отдельный репозиторий, **не ветка RiceEngine**. Название: **voxelforge**.

```
c/                      # libvoxelforge_core — Vulkan на plain C, C ABI
crates/host/            # voxelforge-host — Rust: ввод, стриминг, события, сеть, UI
crates/world/           # voxelforge-world — Rust: иерархия вокселей + тесты (оракул)
shaders/                # GLSL: мешер, симуляция, камера
docs/
```

Бинарник — `voxelforge`. Ключ брика упаковывается в `u64`:
`level (3 бита) + 3 × 20 бит знаковых координат` — при базе 8 см и глубине 6
покрывает планетарный диапазон без переполнения.

`SandboxGame` остаётся эталоном до паритета по headless-метрикам.

## Переменные воксели — основа движка

Воксели разных размеров: один и тот же мир содержит и грубые ячейки (большие
объекты), и мелкие (детали), без взрыва по количеству.

**Основа — только BCC** (Соммервилля №1, 6 тетр на кубическую ячейку). Tet-oct в
voxelforge не переносится; из `SandboxGame` берётся сантехника (indirect-диспатч,
brick storage, стриминг, вода), но не мешер.

**Представление** (решение фиксируется до кода):

- воксел — ячейка BCC-решётки уровня `L`: `(level, x, y, z)`, шаг решётки
  `base · 2^level`, координаты целые на своём уровне; плотность живёт в узлах
  решётки, интерполянт — кусочно-линейный по тетрам (один и тот же для рендера,
  коллизии и мешера);
- хранение — **brick map**: брик = кубический кластер 8³ BCC-ячеек (3072 тетры),
  разреженный хеш координат брика → индекс, дальше плотный массив; одна
  индексация на брик, по-воксельного pointer chasing нет;
- подразбиение — **red 8→1**, конгруэнтное, поэтому решётка самоподобна при
  масштабе 2: брик уровня L даёт 8 бриков уровня L+1, а case-table мешера
  (16 случаев на тетру) **одинаков на всех уровнях**. Вот главный выигрыш BCC у
  кубов: таблиц переходных ячеек не нужно вообще (Transvoxel — это про кубы);
- закрытие соседей — red-green замыкание на мелкой стороне, тем же case-table;
- **политика уточнения отделена от представления**: `targetLevel(...)` —
  подключаемая чистая функция. Сейчас тривиальная (всё на базовом уровне), LOD
  как политика добавляется позже без перестройки структур.

**Детерминизм на BCC даётся почти бесплатно**: барицентрические веса в разбиении
BCC на 6 тетр диадические (1/2, 1/4, 1/8), а диадические дроби в float32 точны —
значит интерполяция и все сравнения знаков совпадают у всех вендоров. Вместе с
квантованными целыми значениями поля это делает мешер и коллизию бит-в-бит
одинаковыми на AMD, NVIDIA и Intel.

**Правка** — это запись в узлы решётки + уточнение, а не «поставить куб»: кисть
обязана быть level-aware (raycast по иерархии бриков → refine до уровня кисти →
запись узлов → журнал).


**Откат правок — это операции над деревом**, а не значения вокселов:
`SUBDIVIDE`, `COLLAPSE`, `SET_MATERIAL`. Журнал правок и undo-лог пишутся в этих
терминах, иначе подразбиение необратимо.

**Детерминизм** держится на двух вещах: целые координаты и правило уточнения,
считающееся по целой метрике (никаких float-порогов с `sqrt`). Раскладка памяти
(какой брик в каком слоте пула) — локальная, никогда не реплицируется.

**Один сэмплер на всех**: `sample(level, coord)` используется рендером, физикой
и стримингом. Разные сэмплеры = расходящаяся геометрия коллизий.

## Физика: три солвера, а не один

Разные взаимодействия параллелятся по-разному, и сводить их в один шаг — главная
ошибка. Три независимых солвера, каждый со своим буфером и своим шагом:

| Солвер | Как параллелится | Детерминизм | Риск |
|---|---|---|---|
| обломки (жёсткие тела) | плохо: scatter, дивергенция, итерации с глобальной связью | только gather/Jacobi | стабильность при разных массах |
| тепло | идеально: stencil по узлам решётки | полный | CFL на мелком уровне |
| фазовые переходы и слияние | хорошо: клеточный автомат, двойной буфер | полный, если нет атомиков | глобальная связь через сохранение объёма |

**Обломки.** Потолок определяется не FLOPs, а латентностью и сходимостью.
Работающие правила: пре-фрактура (Voronoi) на CPU/приготовлении, а не разрушение
в рантайме; отношения масс обломков в пределах 8:1, крупные объекты для мелких —
кинематические (бесконечная масса) — это снимает связь в солвере и стоит ноль;
фиксированное число итераций; сон + **запекание** уснувшего обломка в поле
вокселей. Честная стопка из 10k тел не получится; 1–5k тел и «пена» из частиц —
получится.

**Тепло.** Лучший случай для GPU: gather-шаблон по узлам, источник — по контактам
(поток = сила трения × относительная скорость). Ограничение: явная схема требует
`dt ≤ h²/(6α)`, на шаге 8 см это вынуждает либо много подшагов, либо **тепловую
сетку крупнее воксельной** — считать тепло на уровне бриков, а не узлов.
Диффузия на уровне брика в 64 раза дешевле на единицу объёма.

**Слияние.** В воксельном представлении это не булева операция над мешами, а
**объединение полей**: растеризуем оба объекта в одну решётку, мешер выдаёт одну
поверхность. Это ключевой выигрыш воксельного подхода. Но требуется: одинаковый
уровень на поверхности контакта (refine перед слиянием) и фазовый переход
melt → flow → solidify, то есть воксельная жидкость. Самый дорогой по времени
разработки кусок — делать последним.

**Правила для сети.** Обломки и слияние — производные симуляции. Клиент
предсказывает только косметику (частицы, искры); необратимое изменение топологии
решает сервер и рассылает как структурные правки журнала.

**Порядок внедрения:** тепло → обломки с пре-фрактурой → фазовые переходы.
Каждый следующий пункт зависит от предыдущего (слияние требует тепла и
разрушения).

## Что не делать

- Не переписывать на Rust до того, как архитектура зафиксирована.
- Не делать вторую реализацию физики на CPU для сервера.
- Не брать fixed-point арифметику (её на GPU нет; целые — для хранения и ключей).
- Не строить rollback: детерминизма между вендорами нет.
- Не брать `wgpu`: он не отдаёт device addresses, indirect counts, timeline
  semaphores и mesh shaders.
- Не цитировать lavapipe как производительность.

## Риски

| Риск | Когда бьёт | Ответ |
|---|---|---|
| C-слой разрастается | этап 5–6 | бюджет ~5k строк, ревью на «логику в C» |
| Отладка без детерминизма | этап 7 | фиксированный сид, запись снапшотов, snapshot differ |
| Сервер без GPU | этап 7 | lavapipe-замер до обещаний, иначе хост игрока |
| Драйвер виснет на долгих compute | любой | короткие диспатчи, device-side assert, никаких persistent kernels |
