# voxelforge

Воксельный движок, в котором симуляция и рендер живут в памяти видеокарты.
Мир — решётка BCC с вокселями **разных размеров**: в одном мире соседствуют
грубые ячейки для больших объектов и мелкие для деталей, без взрыва по
количеству. CPU занимается окном, вводом, диском и сетью — и больше ничем.

Ближайшая цель — **не игра**, а набор демо-сцен с физическими симуляциями.
Каждая демка одновременно является приёмочным тестом: у неё есть измеримый
критерий прохождения, и она гоняется headless в CI.

```
crates/host  ──►  c/libvoxelforge_core  ──►  Vulkan
   ввод, I/O,        устройство, кадр,           │
   события, сеть     пайплайны, submit           ▼
        ▲                                    VRAM: поле, тела,
        └──────── события + снапшоты ────────  очереди работ
```

## Зачем отдельный движок

Это не ветка RiceEngine и не набор фич поверх него. Причины конкретные:

1. **Контракт кадра другой.** RiceEngine строит кадр как набор объектов с
   материалами и вызовами отрисовки с CPU. GPU-driven кадр — это один командный
   буфер, записанный один раз, где все размеры работ берутся из SSBO. Это
   несовместимые модели, а не разный уровень оптимизации.
2. **Мир другой.** BCC-решётка с переменным размером ячейки, brick map,
   red 8→1 рефайнмент, журнал правок — движок должен *быть* этой структурой,
   а не хранить сцену из мешей и материалов.
3. **Физика — часть представления мира.** Контакты читают то же поле, что и
   мешер; гравитация берёт моменты из тех же бриков. Разделять «движок» и
   «физику» тут нельзя.
4. **Сеть определяет формат мира.** Реплицируется журнал правок, а не поле.
   Это решение принимается до первой строки, а не после.
5. **Языки по сильным сторонам.** Vulkan-граница на plain C (её читает
   `bindgen`, у неё стабильный ABI), состояние и логика на Rust (компилятор как
   оракул). Граница тонкая и однонаправленная.

## Демо и приёмочные тесты

Демки — это и есть дорожная карта. Каждая проверяет конкретную подсистему и
падает, если подсистема сломалась.

| ID | Демо | Что проверяет | Критерий прохождения | Статус |
|---|---|---|---|---|
| **D0** | гравитация: N тел по орбитам | Kepler / симплектический интегратор, локальная СО, детерминизм gather | орбита замыкается за 10 периодов, дрейф энергии < 1% | ✅ 2.2e-5, 1.3e-11 |
| **D1** | падение на планету: тело против поля | контакт «тело ↔ террейн», камера, кадр | ящик лёг и стоит: просадка < 1 см, дрожание < 1 мм/кадр | ✅ 0.5 мм, скорость 0 |
| **D2** | стопка: N ящиков на планете | сходимость контактов, подшаги, отношения масс | стопка из 10 тел стоит 10 с: просадка < 5%, скорость нижнего < 1 см/с | ✅ 0.58%, скорость 0 |
| **D3** | куча: 5k тел на планете | broadphase, CSR, сон, острова | все уснули за < 5 с, физика < 3 мс/кадр | ⚠ не сходится (см. Статус) |
| **D3b** | куча «земли» (грануляр) | полоса частиц, угол откоса | куча держит откос, нет разъезжания | — |
| **D4** | правило больших масс κ>1000 | односторонняя связь: лёгкое не тонет и не взлетает | нет выстрела, проникновение < 1 м | ✅ тест `heavy_body_...` |
| **D5** | нагрев и слияние | тепловой stencil, фазовый переход | два тела в контакте сливаются в одну поверхность | — |
| **D6** | обломки с пре-фрактурой | фрагментация, запекание в поле | 1k обломков, все запечены за < 5 с, поле не рвётся | — |

Три правила для демок:

1. **Headless по умолчанию.** Окно — только явным флагом `--window`. Демки не
   должны всплывать на рабочем столе.
2. **Фиксированный сид и фиксированное число шагов.** Демка — эксперимент, а не
   интерактив: одинаковый вход даёт одинаковые метрики.
3. **Метрики в JSON.** Каждая демка печатает числа (просадка, дрейф энергии,
   мс на подсистему), CI сравнивает с порогами. Скриншот — для глаз, метрики —
   для гейта.

Готовые сценарии (CPU-эталон, `crates/refsim`):

```
# орбиты: интегрируется ровно целое число периодов, поэтому closure имеет смысл
cargo run --release -p voxelforge-refsim --bin vf-ref -- \
  --scenario orbit --frames 1500 --periods 2 --substeps 4 \
  --out demos/out/orbit.vfr --svg demos/out/orbit.svg --json demos/out/orbit.json

# гравитационный коллапс облака тел
cargo run --release -p voxelforge-refsim --bin vf-ref -- \
  --scenario collapse --bodies 400 --frames 900 --seed 7 --dt 0.01 \
  --out demos/out/collapse.vfr --svg demos/out/collapse.svg
```

Смотреть: открыть `viewer/index.html` в браузере и перетащить туда `.vfr`
(файл читается локально, сервер не нужен). Либо сразу получить картинку
через `--svg`. Бинарник падает с ненулевым кодом, если дрейф энергии > 1%
или орбита не замкнулась за 1% — это и есть CI-гейт демки.

Про D3b отдельно: «куча земли, которая не ломается» — это **гранулярная среда**,
а не жёсткие тела. Держать вертикальную стену из сыпучего она не будет ни при
каком солвере; критерий должен быть «угол естественного откоса», а не
«жёсткость стопки». Если нужна связная земля — это другая модель (когезия),
и это отдельное решение.

## Возможности

### Мир
- Воксел = `(level, x, y, z)` на BCC-решётке (Соммервилля №1, 6 тетр на
  кубическую ячейку); размер в мире `base · 2^level`.
- Bricks 8³ BCC-ячеек (3072 тетры, 9³ узлов поля), разреженный хеш по `u64`-ключу
  `level(3) | x(20) | y(20) | z(20)`.
- Подразбиение red 8→1 — конгруэнтное, поэтому case-table мешера одинаков на всех
  уровнях, а переходные таблицы не нужны вовсе.
- Политика уточнения (`targetLevel`) отделена от представления: LOD — это
  политика, а не структура данных.

### Кадр
- Один командный буфер на образ swapchain, записан один раз, пере-сабмитится.
- Все размеры работ — indirect из SSBO (`DispatchIndirect`,
  `DrawIndirectCount`); CPU не знает, что и сколько рисуется.
- Bindless input-ring: CPU пишет слот, GPU читает по индексу кадра.
- Число шагов симуляции за кадр решает GPU (аккумулятор времени в VRAM).

### Физика
- Три независимых солвера: **тела** (XPBD, gather по CSR, подшаги),
  **тепло** (stencil на бриковом уровне), **фазовые переходы** (клеточный
  автомат, слияние = объединение полей).
- Все тела динамические. Пара с отношением масс > 1000:1 решается односторонне:
  партнёр бесконечномассовый для этой связи, но его скорость читается, а реакция
  применяется честно. Погрешность `O(m/M)` — 0.1% на пороге.
- Сэндвич (малое тело между двумя тяжёлыми) промотируется в пару «партнёр–
  партнёр» с ограничением по зазору.
- Прыгучесть по умолчанию `e = 0`: упругость — свойство материала, а не базовое
  поведение, и главный источник энергии из ниоткуда при плохой сходимости.
- Гравитация: радиальная аналитика для планет, мультиполи по brick map для
  неоднородной плотности, Kepler для орбит. Два слоя времени — орбитальный и
  локальный.

### GPU → CPU
- Два канала: **события** (32-байтные записи, лог на кадр в полёте, чтение слота
  N−2 без стойки) и **снапшоты** (bulk-копия на сетевом тике).
- Одноразовые события — через `atomicExchange`, порядок не определён (несёт
  индекс шага).
- Каждое событие расщеплено: эффект на GPU сразу, уведомление CPU позже.

### Сеть (отложено до D2–D4)
- State-sync: сервер авторитетен, клиент экстраполирует и сглаживает; rollback
  невозможен (нет кросс-вендорного детерминизма).
- Реплицируется журнал правок (`SUBDIVIDE`, `COLLAPSE`, `SET_MATERIAL`), не поле.
- Hit-валидация — откат позиций целей из истории снапшотов, не симуляции.
- Авторитетный сервер — lavapipe (те же шейдеры на CPU-Vulkan) или хост игрока.

### Детерминизм
- Гейт 1: `det.h` — макросы падают на именованных `sqrt/sin/pow`.
- Гейт 2: скан SPIR-V на `OpExtInst`/`OpAtomic` (ловит `normalize()`).
- Гейт 3: twin-run `memcmp` — ловит гонки, которые статика не видит.
- Солвер gather-only: читаю прошлый шаг, пишу свой слот, атомиков нет.

## Архитектура репозитория

```
c/                  libvoxelforge_core — Vulkan на plain C, C ABI (~30 функций),
                    без логики, без состояния мира, вызовы только Rust → C
crates/host/        ввод, кольцо ввода, стриминг, дренаж событий, сеть, UI
crates/world/       иерархия вокселей, правки, журнал + тесты (оракул)
crates/refsim/      CPU-эталон физики: гравитация, интегратор, запись треков,
                    CLI vf-ref (сценарии + метрики + SVG)
viewer/             index.html — просмотр записанных треков в браузере
demos/out/          результаты прогонов (.vfr, .svg, .json), в git не идут
shaders/            GLSL: мешер, солвер, камера, физика
docs/               план и решения
```

## Дорожная карта

| Шаг | Содержание | Проверка |
|---|---|---|
| **M0** | каркас: C-ядро (устройство, swapchain, один записанный CB), Rust-хост, headless на lavapipe | чёрный кадр + измеренное CPU-время кадра |
| **M1** | BCC-мешер на смешанных уровнях, red-green замыкание, тесты иерархии | соотношение вокселей одноуровнево vs многоуровнево ≥ 5× |
| **M2** | правка: raycast по иерархии, refine, запись узлов, undo-журнал | рисуешь и подразбиваешь, мешер трогает только грязные брики |
| **M3** | D0 → D1 → D2: гравитация, посадка, стопка | критерии из таблицы демок |
| **M4** | D3, D3b, D4: куча, грануляр, крупные столкновения | критерии из таблицы демок |
| **M5** | D5, D6: тепло, слияние, обломки | критерии из таблицы демок |
| **M6** | LOD-политика, затем сеть | — |

## Сборка и окружение

```bash
nix develop                     # rustc 1.99.1, glslc 2026.1, spirv-tools, mesa/lavapipe, gcc
cargo test --locked             # 4 юнит-теста эталона
nix flake check                 # юнит-тесты + демка D0 как приёмочный гейт
nix build                       # бинарник vf-ref из зафиксированных исходников
```

Демки запускаются прямо через `nix run` — без dev shell и без клонирования:

```bash
nix run                                    # список демок
nix run .#orbit                            # орбиты → demos/out/orbit.{vfr,svg,json}
nix run .#collapse                         # коллапс → demos/out/collapse.*
nix run .#orbit -- --frames 3000 --periods 4   # свои параметры (перекрывают дефолты)
OUT_DIR=/tmp/demo nix run .#orbit          # свой каталог для результатов
nix run .#vf-ref -- --scenario orbit --frames 1500   # прямой доступ к CLI
```

Важно: `nix run .#vf-ref` с грубыми параметрами (например `--frames 60`) **падает
намеренно** — при 4 подшагах и 2 периодах шаг получается слишком крупным, и гейт
«орбита не замкнулась за 1%» срабатывает. Это не поломка, а работающий тест;
дефолты в `.#orbit` подобраны так, чтобы проходить.

Почему это соберётся через год:

| Что пинует | Чем |
|---|---|
| тулчейн (rustc, glslc, spirv-tools, mesa, gcc) | `flake.lock` — точная ревизия nixpkgs (2026-11-21) |
| крейты | `Cargo.lock` в репозитории + `--locked` везде, включая CI |
| сборку в CI | CI идёт через тот же flake, а не через `rustup` с плавающей версией |

Обновление версий — **осознанное действие отдельным коммитом**, а не побочный
эффект сборки:

```bash
nix flake update && nix flake check && cargo update && cargo test --locked
```

`VK_ICD_FILENAMES` в dev shell автоматически указывает на lavapipe, поэтому
любой прогон Vulkan-кода по умолчанию идёт на программном драйвере и не
касается видеокарты. Реальный GPU — только явным `VK_ICD_FILENAMES=` override.

## Принципы

- Архитектура раньше языка. За тонким C ABI язык хоста меняется дёшево.
- C-слой — меньше ~5k строк и без алгоритмов: без RAII, без проверок, он должен
  быть скучным.
- Gather вместо атомиков. Float-атомики запрещены: они не ассоциативны, значит
  недетерминированы.
- Никаких persistent kernels и долгих диспатчей: на Linux нет TDR, зависший шейдер
  вешает GPU до сброса.
- Фиксированное число подшагов. Адаптивные ломают детерминизм и сеть.
- lavapipe — для корректности и CI. Производительность на нём не измеряется.
- Один сэмплер поля на рендер, физику и стриминг.
- Демка без числового критерия — не демка, а скриншот.

## Статус

CPU-эталон: D0, D1, D2 и правило больших масс (D4) проходят, 9 тестов зелёные,
один отключён. Вьюер — WebGPU, 3D: орбита мышью, зум колесом, пан ПКМ/Shift.

**D3 (плотная куча) не сходится, и это записано честно.** Замеры: тела получают
до 25 м/с, куча расползается в один слой вместо пирамиды, проникновение в первые
секунды доходит до 12 см. Причина не в константах: скорость выводится из позиций
(`v = Δx/h`), поэтому каждая коррекция проникновения превращается в скорость, а
в плотной куче коррекции не успевают разрешиться за фиксированные итерации и
накапливаются в «фонтан». Промежуточные меры (контактный зазор, релаксация,
потолок скорости, живущие между подшагами опоры трения) улучшают картину, но не
лечат причину.

Что из этого следует для GPU-версии: контактный слой нужно писать сразу
скоростным (импульсы с bias и warm start), а не переносить позиционный солвер.
Эталон D1/D2 при этом остаётся годным — там контакты разреженные, и он даёт
цифры для сверки.
